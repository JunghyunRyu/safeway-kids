- 신청서가 "이미 동작한다"고 쓴 13개 주장 중 **코드로 확인되는 것은 4개**(C3 일부, C6 일부, C10, C13 일부)다.
- **AI 기능은 하나도 동작하지 않는다.** LLM 클라이언트는 무조건 Stub을 반환하고(`backend/app/modules/ai/factory.py:18-25`), AI 5축 설계서가 정한 구현 파일 10개가 저장소 전체(모든 브랜치 포함)에 없다.
- 4/29 AI 차별화 Tech Spec과 4/30 Todo Plan(5/20~5/30 구현 예정)이 있었지만 **구현되지 않았다**. 신청서는 그 설계를 구현 완료처럼 서술했다.
- 사고 대응은 **보호자 화면의 SOS 버튼 → 플랫폼 관리자 알림**까지만 있다. 정작 개를 데리고 걷는 **산책 파트너(walker) 화면에는 긴급 버튼이 없다.**
- 1단계(보호소 1곳·산책 30건)는 **AI 없이도 돌릴 수 있다.** 꼭 고쳐야 하는 코드는 S급 3건이고, AI 공고 초안은 앱 밖에서 수동으로 품질부터 확인하는 편이 맞다(§5).

## 5. 1단계 최소 범위 제안
### 꼭 만들 것 (합계 S×3, 약 1~2일)
1. **walker 화면 SOS** — 기존 `POST /pt/sos` 재사용 + `tel:119` + 인근 동물병원 지도 검색 링크. 보호자가 아니라 **걷는 사람이 누르는 버튼**이어야 신청서 해결 1과 맞는다
2. **무상 산책 허용** — `price` 0 허용(보호소 예약일 때만) 또는 보호소 예약 플래그
3. **SOS 알림 대상에 보호소 담당자 포함** — 지금은 플랫폼 관리자에게만 간다

### 수동으로 대신할 것
- 보호소 계정·동물 등록·파트너 승인 (§4의 1~3)
- **입양 공고 초안**: 산책 사진·메모를 운영자가 모아 앱 밖에서 LLM으로 초안을 만들고, 보호소 담당자에게 "쓸 만한가"를 묻는다. 신청서 1단계 지표("입양 공고 초안이 실제로 쓸 만한 품질인지")를 **AI 기능을 만들기 전에** 측정할 수 있다. 쓸 만하다는 답이 나오면 그때 축 B를 만든다 (L, 약 3~5일: LLM 클라이언트 + `generate_caption` + 사진 업로드 연결)

### 미룰 것 (1단계 결과를 보고 결정)
| 기능 | 공수 | 다시 볼 조건 |
|---|---|---|
| 축 E GPS 이탈·정지 감지 + check-in | M | 산책 30건 중 실제 이탈·장시간 정지 사례가 나오면 |
| 축 A 사고 자동 분류 | M | 사고·준사고가 1건 이상 기록되면 |

| 보호소 기관 계정·다수 동물 관리 | M~L | 2단계 진입 조건(재사용 의사) 충족 시 |
