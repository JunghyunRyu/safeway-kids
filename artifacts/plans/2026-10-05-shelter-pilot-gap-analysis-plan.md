# 보호소 시범 운영 기능 차이 분석 — 계획

## 1. 왜 하는가
2차 신청서는 보호소를 고객으로 세 가지 기능을 약속했다. 또 Q3-1에 **"위 세 가지는 계획이 아닙니다. 1차 신청 당시 … 동작을 확인한 기능들"** 이라고 적었다.
통과하면 1단계 진입 조건이 "보호소 1곳 확보 → 산책 30건 운영"이다. 그때 무엇을 만들어야 하는지 지금 알아 두어야 한다.
떨어져도 결과물은 다음 지원사업(예비창업패키지 등)과 보호소 영업 자료로 다시 쓴다.

## 2. 범위
| 포함 | 제외 |
|---|---|
| 신청서 약속 → 현재 코드 대조표 | 코드 수정·신규 기능 구현 (Tech Spec 전에는 금지, CLAUDE.md 규칙 3) |
| 보호소 운영 흐름에 필요한데 없는 것 | 지자체 이용료 가격 설계 (R-6, 별도 작업) |
| 신청서 문구 중 코드와 어긋나는 주장 목록 | 앱스토어 출시 준비 |
| 1단계(산책 30건) 최소 구현 범위 제안 | SafeWay·CareConnect |

## 3. 사전 관찰 (키워드 탐색일 뿐, 검증 아님)
- PT 역할은 **owner(보호자) / walker(산책 파트너)** 두 가지다. 보호소(기관) 역할·엔티티는 없다
- PT 모델 11개: Pet · WalkerQualification · WalkerAvailability · PtBooking · WalkSession · WalkGpsHistory · WalkerWallet · WalkerReview · PtPayment · WalkPhoto (+caption 상태 enum)
- `incident`·`emotion`·`moderation` 키워드가 PT 백엔드·모바일·공용 모듈에서 0건이다. → 약속 ①(1탭 사고 대응)과 ③(감정 톤 리포트)이 실제로 있는지 **최우선 확인 대상**
- `sos`는 11건이지만 SafeWay 모듈일 가능성이 높다. PT에서 쓰이는지 확인 필요

### M2. 코드 대조 (2~3시간, 읽기만)
- 항목마다 판정: **동작 확인됨(테스트 있음)** / **코드 있음·테스트 없음** / **일부만** / **없음**
- 근거는 `파일:줄` + 해당 테스트 이름. pytest·jest는 앱 디렉토리에서 실행해 현재 통과 여부를 확인한다
- 1차 탐색은 `Explore` 에이전트 1개로 범위를 정하고, 판정은 직접 읽고 내린다

### M3. 보호소 운영 흐름 차이 (1~2시간)
보호소 하루 흐름으로 보며 빠진 것을 찾는다:
1. 보호소 계정·담당자 로그인 → 2. 보호 동물 일괄 등록(개인 소유 아님) → 3. 파트너 신청·승인 → 4. 산책 배정·반출 확인 → 5. 산책 중 모니터링·사고 대응 → 6. 반납 확인 → 7. 기록 열람·입양 공고 초안 내보내기
- 개인 보호자 모델(owner가 Pet 소유, Booking에 결제)과 보호소 모델(기관이 다수 동물 보유, 결제 없음)의 구조 차이를 정리한다
- `ux-advocate` 1회 검토 (보호소 담당자·파트너 관점)
